# Step37：官方样例对照的判断与离线审核方案

日期：2026-11-10（北京时间）。结论：建议采用官方完整样例作为下一轮对照，先隔离构建与审核，再决定是否进行一次受控初始化/停止；本轮不直接运行样例、不生成正式修复 DLL。

## 四项判断

| 问题 | 判断 |
| --- | --- |
| 下一步是否编译并运行 pt_install_test.dll | 应采用官方样例作对照，但分阶段。先按原样例真实 Makefile 的同步 x64 DLL 目标在隔离工作副本构建；保留源码与资源，审核初始化/终止及自动回调，再安排无模型操作的受控观察。不未经审核直接运行。 |
| 官方样例也失败是否优先判定许可/解锁问题 | 优先核查许可，但不能直接判定。实际得到 PRO_TK_APP_UNLOCK 或明确许可提示时，才有依据定位到文档描述的开发许可/解锁条件；泛化启动失败也可能来自错误目标、资源、注册、路径或构建环境。 |
| 官方样例成功后是否回头比对空 DLL | 是。用成功样例建立对照基线，先比较实际构建/链接与宿主契约，再逐项比较 SDK 验证调用、初始化及资源差异，不一次复制所有 API 或菜单逻辑。 |
| 是否进入业务转换或修改 config.pro | 否。对照最多验证样例自身的初始化/停止链路，不打开、修改或保存模型，不触发样例业务命令，不改 config.pro。 |

本轮依据是用户提供的本机审核摘要，并非云端取得的 sample-contract-audit.json、SDK 原头或样例原件。记录“未发现 .def/额外导出候选”，不扩大为“所有条件和隐含契约已被穷尽证明”。原型及 DAT 结构与样例一致的摘要，已降低继续盲改这两项的优先级。

## 新结果如何改变方向

- 按摘要，TestInstall.c 的 user_initialize 与现有工程签名一致，官方 protk.dat_dll 字段结构也一致。当前不改签名、version/build、成功返回值或 DAT 结构，不增加猜测的导出。
- ProToolkitDll.h 中 PRO_TK_APP_UNLOCK 的说明提供了明确的可判别分支，但当前尚未观测到这个状态。ProToolkitDllLoad 的文档错误列表不能反推出辅助应用界面本次内部究竟返回什么。
- 官方样例没有在空入口内执行 unlock，不等于运行永远不需许可或二进制解锁条件；不能在 user_initialize 里添加猜测的解锁逻辑，也不根据 _NU 后缀推断运行资格。
- 官方样例调用 ProWcharSizeVerify、ProCmdActionAdd 等 API，是待对比的真实差异。不能据此断言每个空 DLL 都必须注册命令；也不能在没有准确原型和调用契约时自行补调用。

## Makefile 工程必须跟踪实际构建入口

ConfigurationType=Makefile 时，应查看适用配置的 NMakeBuildCommandLine，追踪它调用的 makefile、目标、宏、环境及输出。v143 可能只是项目元数据，不能代替真实 cl/link 命令或证明所有配置均使用相同工具集。不能直接照抄本工程的链接命令去重建官方样例，也不凭 pt_install_test.dll 这个名字猜 nmake 目标。

本包升级只读工具，增加 NMakeBuildCommandLine、ReBuild/CleanCommandLine、NMakeOutput、预处理宏和搜索路径“是否存在”的派生记录。命令只作数据处理，原始命令及绝对路径不写入输出，也不会执行。输出 schema_version=2，保留旧字段并增加 NMake 派生信息；旧审核结果不代表已读取这些新增字段。项目条件、导入与 make 变量仍不求值；报告不能替代人工读取实际生效的命令。

示例（已有 Python 3 的离线工作机或云端；无解释器时不要求在 Creo 现场安装）：

```sh
python3 tools/audit_sample_contract.py --sample-zip "<真实protk_install_example.zip>" --dll-header "<真实ProToolkitDll.h>" --dll-header "<真实ProToolkit.h>" --output-dir "<新的离线审核目录>"
```

不要因为工具看见 Clean/ReBuild 字段就执行清理。仅在隔离副本中执行已经人工审核过的构建目标；不修改安装中的 SDK 样例或覆盖已加载 DLL。

## 对照组离线准备

1. 保留官方样例源码、makefile、配置与资源身份；对照组第一版不改入口、不加入我们的日志、不删菜单或 API，以免失去官方样例基线。
2. 选中实际的同步 x64 DLL 构建目标；核实真实工具链、SDK、CRT、宏和完整构建命令，记录退出码及产物散列。若原工程输出是 EXE 或其他模式，先查正确目标，不能以启动方式猜改。
3. 保留原版 text 目录、消息/本地化及其他资源，按官方 protk.dat_dll 实际字段填写副本。不能沿用空探针的空 text_dir；样例注册命令可能需要其资源，资源缺失会污染对照结论。
4. 审核原样例的构建前后步骤、DllMain/全局初始化（如有）、user_initialize、user_terminate 及自动回调。确认初始化和停止不会加载、创建、修改、保存模型或自动触发业务命令。仅知道两个 API 名称不足以完成此审核。
5. 离线检查产物 x64/DLL、入口导出、依赖和注册路径；保留 DLL 原名及资源布局。不要把某个文件重命名后仍假定所有样例硬编码引用可用。记录已知运行/开发条件，不安装、采购或猜测解锁。

本轮没有样例原件和 Windows/真实 C SDK 构建环境，以上构建与源路径审核尚未由云端执行；包内不提供伪称准确的 nmake 命令、补造 SDK 头或已编译 DLL。

## 后续受控观察范围

只有离线构建/资源/源路径审核满足后，才安排独立的样例观察。人工准备空模型会话，用本版支持的临时注册方式，记录实际注册、启动提示及状态；不改 config.pro、不自动启动 Creo、不覆盖旧条目，不点击样例业务命令。

预先核对样例是否支持停止及其终止语义。若不支持，不强加 allow_stop true 声称可卸载，也不将该次观察设计为无条件可停止测试。启动/停止失败即保留证据并结束尝试，不自动重试、结束进程或删除模块。此方案不是现在要求现场部署；本包没有执行任何注册或运行。

记录准确错误文字或实际 SDK 返回名；只有泛化界面提示时保持具体码未知。不要为取得错误码临时制造另一个未经审核的加载器，LoadLibrary 成功也不能替代 TOOLKIT 注册验证。

## 对照结果分支

| 实际结果 | 如何解释与后续动作 |
| --- | --- |
| 官方样例明确返回 PRO_TK_APP_UNLOCK/明确许可提示 | 按本版官方说明核对当前会话开发许可及该二进制适用的解锁条件；暂停继续改 C++。不从源码没有 unlock 推断无需许可。 |
| 官方样例仅显示泛化失败 | 仍未唯一定位许可。先确认正确目标、资源、DAT、实际构建和输出身份，再依据具体日志缩小范围，不继续试错初始化代码。 |
| 官方样例成功初始化 | 证明该样例在该会话与资源/注册条件下的链路可用；不是对所有 DLL、许可范围、API 或业务写操作的认证。固定这份成功基线。 |
| 官方样例尚未构建或无法完成源码审核 | 保留离线准备状态，不把计划填写为成功，不进入业务模型操作。 |

官方样例成功后，将其与空 DLL 的实际构建、链接输入/可用链接映射、被提取的 SDK 库成员、资源布局、验证 API 和入口返回路径逐项比较。只有真实证据表明某 SDK 验证或引导要求缺失，才制作单项补丁；ProCmdActionAdd 等菜单逻辑不自动成为最小 DLL 必须项。下一次变化继续保持不写模型，不恢复 Java/WFC 路线。
