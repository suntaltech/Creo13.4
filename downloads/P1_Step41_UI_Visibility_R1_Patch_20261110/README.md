# Step41 UI R1：仅缩短第三项消息文件名

日期：2026-11-10（北京时间）。本轮只改变一个变量：第三个 ProCmdDesignate 使用的消息文件 basename，从 p1_readonly_body_face_count.txt 改为 p1_fc.txt。新文件内容与交接包原文件逐字节相同，计数实现完全不动。

## 1. 改了什么文件

- src/entry.cpp：只替换一个宽字符串字面量，L"p1_readonly_body_face_count.txt" → L"p1_fc.txt"。
- text/p1_fc.txt：原消息文件的原样短名副本，不改键名、标签、说明或空行格式。
- patches/ui-message-basename.diff：一个补丁，包含上述一行替换和新资源副本。原长名文件保留为基线，不删除。

基线 entry.cpp SHA256：fdd9fd0dccfe2f20f5a84336bbd5720a6fb3a68cb187fb374bb316e4a7b1322c。可直接覆盖隔离副本中的源码，或核对基线后执行 git apply --unidiff-zero --check，再用 --whitespace=nowarn 应用同一 diff。消息末尾空行是记录格式，不能自动清理。

## 2. 为什么改

原始启动 JSONL 显示三个命令均 ActionAdd=0、Designate=0，最终初始化返回 0；截图显示第三个命令在 TOOLKIT 命令列表中缺失，交接说明完整重启也未解决。注册成功、指定调用成功与 UI 列表可见必须分开记录。本次没有 BODY_FACE_COUNT_ENTER/RETURN，面计数运行验收仍未完成。

直接比较源码，三组调用均使用 uiProeImmediate、readonly_ping_access、PRO_B_TRUE/PRO_B_TRUE，ProCmdDesignate 参数顺序也一致。第三项引用的三个消息键都能在随附文本中找到，文本是 ASCII、无 BOM，四行记录格式与可用 Ping 文本一致。没有发现第三项独有的参数错位或访问回调条件。

| 项目 | Ping | Model Info | Body Face Count |
| --- | --- | --- | --- |
| 消息文件名字符数（含 .txt） | 20 | 26 | 31 |
| 注册/指定日志 | 0 / 0 | 0 / 0 | 0 / 0 |
| 当前 UI 观察 | 可见 | 可见 | 不可见 |

文件名是本轮优先测试的资源差异。短名 p1_fc.txt 共 9 个 ASCII 字符，保留所有其他输入，便于判断资源名称/解析关联是否影响可见性。没有本版 SDK 文档或运行结果能证明“31 字符必然违反某个官方上限”，本补丁是单变量定位及修正候选，不把该猜测写成已证实根因。

原面计数描述行有 81 字符，但此前交付的可见 Model Info 描述有 82 字符；本包又没有后者的现场消息原件，因此不能仅凭 81 就断定是描述长度造成。为控制变量，本轮也不缩短该行。文本中的 array length 是旧文案，本轮原样保留，不表示实际计数已改成数组；实现仍是已交接的默认体访问器。

## 3. 预期通过时看到什么

本机助手只需：

1. 核对基线与补丁散列，沿用已成功的离线编译/链接参数，保留两个 plus /INCLUDE，不重新采集版本、不改 CRT/DAT/config.pro。必须重编这个新源码的对象再链接；只复制短名资源而继续使用旧 DLL 不是本变量的有效测试。
2. 把 p1_fc.txt 放到与已成功 p1_readonly_ping.txt 相同的实际消息解析位置。短名副本 SHA256 必须与本包原内容一致。不要同时移动 text_dir、改变语言目录方案或删除旧资源。原包未提供现场资源目录快照，不能把“附件有文件”当作“宿主已读到该文件”。
3. 按既有候选加载流程核对新 DLL 身份，不覆盖加载中的 DLL，不叠加同名旧命令。注册日志预期仍全部为 0；这些码与修改前相同，不足以单独判定修复。
4. 在相同会话/模型条件下查看 TOOLKIT 命令列表一次。应出现的名称仍是 p1_readonly_body_face_count，不是 p1_fc；命令名与显示标签都没改。不要顺带改菜单、图标、优先级或清理全部 UI 设置。
5. 若命令出现，按既有方式绑定并只触发一次。预期 BODY_FACE_COUNT_ENTER 和 BODY_FACE_COUNT_RETURN；无模型时 no_active_model 是正常分支，不需要为了本次 UI 试验额外打开模型。

可见性通过与计数执行通过分别填写：只有列表出现，不能认定访问器已运行；出现 ENTER/RETURN 也要按 result 和 surface_visit_pro_error 判断计数是否完成。计数错误保留原逻辑和证据，不在本轮再改算法。

## 4. 预期失败时如何分支

- 真实编译/链接或 plus 导出失败：先核对候选构建身份及固定链接要求，不修改 UI 参数或计数实现。
- 注册/指定非 0：保留实际返回码，结束本轮，不能与原来“两项均 0 但不可见”的条件混为一谈。
- 新 DLL、短名文件与放置位置均核对后仍不可见：说明“短名这一变化足以解决问题”的假设未通过。保持原始证据，不连续缩短标签、改命令名、加图标或重复重启来凑成功。
- 命令可见：支持该资源 basename/定位关联修正有效，但单次结果仍不证明具体字符数上限或内部缓存实现。不要补写 SDK 没有给出的限制。
- 可见却没有回调日志：保留 UI 与触发两个层次，核对绑定和实际 DLL 身份。停止扩大改动，不改默认体访问器或另建日志通道。

交接包已做过完整重启，本轮不把反复重启、删除缓存或重置全部 Ribbon 当作新的必要步骤。同名注册冲突、旧 DLL 未退出或资源未放置时，先记录“本变量未被有效测试”，不要误判候选结论。

## 5. 不做什么

不改命令名、消息键、显示标签、描述、访问回调、参数顺序、标志或优先级。不改 surface visit/count 逻辑，不新增 API 或诊断调用，不改旧命令、入口签名、返回值、链接要求、DAT 或 config.pro。不打开、选择、修改、保存模型，不自动启动 Creo，不做转换。

本轮只交一个资源名变量补丁，不附采集工具。云端只做字节差异、补丁应用和资源一致性检查，没有真实 SDK 编译或 UI 运行验证。原始截图、日志与私人路径不随包公开。
