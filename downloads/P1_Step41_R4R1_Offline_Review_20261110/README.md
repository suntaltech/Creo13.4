# Step41 R4-R1 失败证据复核与下一步离线补证

日期：2026-11-10（北京时间）。本轮交付审核报告和只读审计脚本，不生成新的 DLL/C++ 候选。先取得确切契约和资源查找证据，再决定下一处修改，避免继续无依据试错。

## 1. 改了什么文件

插件源码、消息资源及注册配置均未改动。

- evidence/runtime-review.json：选取日志最后一次 INIT_ENTER 对应的初始化段，核对 ID 区分及传参映射。
- evidence/resource-review.json：对此前收到、且本机上轮报告哈希一致的三个资源字节做结构审核。
- evidence/verification.json：只读脚本的实际运行及异常输入检查结果。
- tools/audit_resources.py：Python 标准库离线审计工具，不连接 Creo、不加载 DLL；需要显式输入资源目录、日志文件和一个尚不存在的报告输出目录。它不是 SDK 消息解析器。
- next-input.template.json：仅需补齐的缺失证据，不要求重复环境采集。

脚本可供本机助手按需复现（若已有 Python，无需新安装依赖）：

```text
python audit_resources.py --resources <三个资源所在目录> --log <已有R4R1日志> --output <新报告目录>
```

本包已带审核结果，不要求为运行脚本重新采集同一批文件。脚本只读取指定文件并写新报告；不搜索用户磁盘、不改配置、不复制原始日志、不运行 SDK API。源码哈希/DLL完整身份本轮未上传，不能声称已逐字节核对本机源码；新 revision/身份日志证明新增诊断路径已执行。

## 2. 为什么这样处理

最新初始化为 pid=23640、load_token=25534343，前面13条属于较早初始化/终止段，已排除出本次统计。三个身份事件均为 UI_R4_R1_DIAG，SDK 动作键与消息键映射符合预期；三个返回 ID 不同，六个 Add/Designate 返回均为0，INIT_BEFORE_RETURN=0。用户报告已成功加载，截图仍只有 ModelInfo/Ping，未见面计数触发日志。

因此这次加载没有观察到 ID 重复，R4 的格式类型错误也已不再阻断此次运行。不能把 ID 不同或返回成功等同于 UI 可见，更不能认定资源解析已经成功。

资源审核发现：

| 资源 | 显示文字长度 | label键长度 | 描述文字长度 | 审核结果 |
| --- | ---: | ---: | ---: | --- |
| p1_fc.txt | 27 | 24 | 81 | 三键各一次，三组key/value/空行/空行 |
| p1_readonly_model_info.txt | 22 | 28 | 82 | 同样分段，命令已可见 |
| p1_readonly_ping.txt | 16 | 22 | 73 | 同样分段，命令已可见 |

三个资源均为 ASCII，无 BOM/NUL，LF 换行。不能因为面计数描述有81字符，就宣称超过80导致不可见：已可见 ModelInfo 的描述是82字符。面计数的键也短于可见 ModelInfo 的键。面计数显示文字较长，但没有实际字符上限文档，当前不再次通过缩写猜测规则。

p1_fc 的描述仍写着“Read-only array length”，与已实现的访问器计数语义不一致；这是文案问题，不是已证实的可见性根因，本轮保持资源不变，避免夹带变量。

共同文本结构只证明与已工作的样本一致，不证明符合所有 SDK 消息规则，也不证明 Creo 实际读取的文件就是该磁盘副本。本机上轮哈希与我们持有字节一致，故无需再次上传相同资源字节。

## 3. 下一步只需补什么

由本机助手完成以下只读核查，用户无需再做 GUI 点击、注册/启动或编译测试：

1. 已提供 ProCmdActionAdd/ProCmdDesignate 函数声明与 uiCmdCmdId=void*，不要重复。仅补同版 SDK 对 ProCmdDesignate 参数含义、返回码、消息文件查找与 UI 可见性要求的完整注释，以及 ProCmdItemLabel、ProCmdLineHelp、ProCmdDescription、ProFileName 的真实 typedef/上限定义。重点区分“消息键”与“解析后的显示文字”，不能把数组类型长度直接当成所有显示文本的限制。
2. 若头文件只有声明、没有语义注释，明确写“头文件无注释”，再定位本机同版官方帮助中的对应段落，给标题/版本/相关文字；缺失则记录缺失。不要反复收集同一函数声明，不凭经验创造限制或新增 API。
3. 核对当前候选注册条目的 text_dir 指向关系及现有语言子目录。只提供脱敏后的相对目录树（列出三个文件及可能的同名副本）、候选条目与资源根目录的对应关系、当前界面语言，并说明查找先后顺序是否有官方依据。不要修改 DAT/config.pro、不扫描整个磁盘；可以利用已有记录，无需启动 Creo。未有解析证据时，明确区分“文件存在/哈希匹配”与“已证明 Creo 实际读到了它”。

如果本机已有相关官方样例的 Designate 调用与消息格式，可以附最小相关段落和来源版本，作为对照，不整包上传 SDK。填写 next-input.template.json，附上述精确片段即可。

## 4. 预期通过与失败分支

- 离线文档指出明确被违反的约束：带引用定位具体参数或资源差异，再生成一份只修该处的候选。
- 文档没有显示文本上限/格式异常、实际查找关系仍未明确：不把“没有找到规则”写成“规则不存在”，保持未知，先核对查找机制。
- 发现重复资源副本或语言层级差异：记录各相对路径及哈希，不能直接删除/覆盖；依据真实搜索顺序确定后再修一处。
- 文档与磁盘关系都正常但仍不明：后续再选一个有依据的 SDK 原生消息解析观测点；先取得真实声明/返回码语义，不猜函数名、不把 Add/Designate 返回0当作解析证据。

同一 PID 内出现较早 TERM 回调及新加载事件，不能据此推断所有命令/UI缓存均已清除。本轮不删除缓存、不重置UI，也不要求重复重启来碰运气。
