# Step41 UI R4：命令身份与指定元数据诊断候选

日期：2026-11-10（北京时间）。这是离线诊断补丁，不是 UI 修复版本。先完成离线契约/资源审核，再决定是否按既有流程做一次受控观察；不要求现场部署正式版本。

## 1. 改了什么文件

仅 src/entry.cpp 增加一个日志 helper、type_traits 编译检查及三个调用点。每次 ActionAdd 成功、Designate 调用之前，写一条 CMD_IDENTITY_BEFORE_DESIGNATE。记录 SDK 返回的 command_id、实际传入的 SDK 动作键、label/help/description 消息键及消息文件基名。三个命令共增加三条记录；访问回调和逐面遍历不加日志。

原有事件名、facts.command 功能标识保持不变。新事件 revision 为 UI_R4_DIAG。SDK 键仍是 p1_readonly_fc，长功能标识仍是 p1_readonly_body_face_count。日志中的键来自调用点参数，不是 SDK 对已加载文本或 UI 内部状态的回读；message_file 也不是解析后的磁盘路径。ID 仅在同一进程/同一 load_token 中比较，不跨运行比较数值，不凭某个数值推断有效性。

patches/registration-identity.diff 与完整源码等价。核验 evidence/manifest.json 基线哈希后，在隔离副本使用 git apply --unidiff-zero --check，再用 git apply --unidiff-zero 应用补丁。不得在其他基线强行套用。本包不含资源文件、DLL、SDK 或活动 DAT。

## 2. 为什么改

R3 上传源码与交付版一致。最新 pid=23640、load_token=24364750 的 Body → ModelInfo → Ping 顺序已证实，六项 ActionAdd/Designate 均为 0，初始化返回为 0；截图仍未见面计数，且没有面计数触发证据。

R1 短消息文件名、R2 改注册位置、R3 新短动作键均未解决当前条件下的缺失。这些试验不能证明名称完全不受约束，也不能穷尽缓存/资源问题。现在停止继续随机缩写。

调用形式上，三个命令都用相同优先级、标志、access 函数及 Add→Designate 流程；区别仍有动作回调、命令身份及消息元数据。已有日志只记成功码，不记返回 ID，也没有本版完整声明/注释和本轮实际生效的三个资源文件。尚不能确定 ID 关联、资源查找或 GUI 上下文中的具体根因。

本轮唯一逻辑变量是增加注册边界可观测性，不改 UI 注册行为。它用于检测命令 ID 是否重复/关联异常，并把实际传参映射到可核查证据；不能把“加日志”说成修复或宣称 ID 重复已发生。

## 3. 预期通过时看到什么

先由本机助手只读完成下面的离线审核，不重复采集 Creo/JDK/MSVC/SDK 版本：

1. 从本机 Creo 13.4 ProUICmd.h、ProMenuBar.h（以实际归属为准）摘出 ProCmdActionAdd、ProCmdDesignate 的完整声明、参数/返回码注释、uiCmdCmdId typedef，以及注释直接引用的可见性要求。若规则只在本机官方帮助，附对应段落和版本/标题；不得凭记忆增加刷新/图标/菜单 API。
2. 只读定位当前候选注册条目 text_dir 的实际资源查找关系，确认被用到的 p1_fc.txt、p1_readonly_model_info.txt、p1_readonly_ping.txt。提交文件字节/哈希及脱敏后的相对目录树；核查重名副本、语言子目录、键是否存在、重复键、编码/BOM、换行、三段结构及实际显示标签。没有解析证据就标记“磁盘候选文件”，不冒称已证明 Creo 加载了它。当前 R3 包没附资源，旧包中的同名文件不能替代本轮有效文件证据。
3. 核查真实 uiCmdCmdId 定义后编译链接。代码只接受可用 long long 表示大小的整数 ID 类型，编译检查是防误用门；若实际类型不符，停止并回传 typedef，不写强制指针转换、不用自造头文件编过。保持已固定链接库、两个 plus 强制引用、DAT、text_dir 及消息字节不变。按 SOP 核验源码/DLL 哈希、导出和依赖；不要重复工具链调查。

离线证据如果已经明确了契约或资源错误，回传该证据后再做针对性修复，不为本诊断包额外跑现场试验。

确需继续观察时，只沿用已有隔离候选流程，由用户手动执行一次受控加载/列表观察。新日志应有三条身份事件（Body → ModelInfo → Ping），各位于对应 ACTION_ADD_RETURN=0 与 DESIGNATE_RETURN 之间；六个返回码和 INIT_BEFORE_RETURN 仍为 0。记录同一 pid/load_token 的完整初始化段并填写 acceptance.template.json。

期望三个 command_id 不同；这只是身份检查通过，不是 UI 通过。不改变 R3 的模型、模式、显示范围、过滤框或 UI 缓存。可见性只记录实际显示名称与截图；若仍不可见，不要求绑定或点击，也不额外点击两个已验收旧命令。

## 4. 预期失败时如何分支

- 声明/文档缺失：先补上述最小片段及资源证据；不凭返回码推断所有 Designate 元数据已经被解析。
- 编译检查或构建失败：回传具体错误/真实 typedef，标记离线构建失败，停止现场操作。不改业务代码、不绕过编译检查。
- 任一 Add/Designate 非 0：按本机同版文档解释原始码，不与“六项均 0 但不可见”混为一类。Add 失败时没有对应身份日志是预期路径。
- 同一初始化段中 ID 重复：支持进一步审查注册身份/关联，但还不能单凭该日志断言 SDK 内部根因；回传原始数值与真实契约，不覆盖旧 ID，不自动重新注册。
- 三个 ID 不同、映射符合预期、六项均 0但仍不可见：本候选未修复。结合实际资源与本版 Designate 文档继续定位；不再猜名称长度、随意增加图标、刷新或新增菜单。
- 缺少新事件：先核对加载的 DLL 身份、初始化是否走到该位置、日志 I/O 失败信号及同一 load_token；不直接认定 SDK 未调用。
- 新候选突然可见：只记录观察结果；本轮只增加日志，不能认定已发现稳定修复或把原因归结为某条元数据规则。身份不明时不点击。若后续验收触发，仍需独立证明 BODY_FACE_COUNT_ENTER/RETURN，不把 UI 可见等同于计数通过。

## 5. 不做什么

不改动作名、显示标签、消息键、描述、文件名、资源字节、注册顺序、优先级、标志或 access；不改三个业务回调、面计数算法、入口签名或返回值；不新增 SDK API、别名、菜单或图标。不改日志存储位置/格式框架，不输出每面日志。

不打开、选择、修改、保存或转换模型，不自动启动/停止 Creo，不改 DAT/config.pro、CRT、链接引导，不删除缓存或重置 UI。云端只做源码和补丁静态验证，没有真实 SDK 编译、Creo 加载或 UI 验证。原始截图、用户本机路径及原始日志不随公开交付包再分发。
