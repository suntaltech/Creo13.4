# Step41 R6：有界 SDK 消息解析探针

日期：2026-11-11（北京时间）。仅增加初始化阶段的四次消息缓冲解析及诊断日志；不是 UI 修复，不获取实际文件路径，不转换模型。

## 1. 改了什么

src/entry.cpp 基于已核对的 R4-R1 源码，基线 SHA256 为 7645a55221b1f806e5951290b84ee2eb0e2684a6baa1d9a24753e7b9230dba11。R5 未改源码，本轮继续保留 R5 两语言资源。

- 在所有 SDK 头文件之前定义 PRO_USE_VAR_ARGS（若已定义则保留），加入 ProMessage.h。依据提供的官方 C++ makefile 和真实受宏保护原型；无需修改本机 build.cmd 或猜额外编译标志。
- 原来三个命令注册函数执行完毕后、INIT_BEFORE_RETURN 之前，顺序解析 body_label、body_help、body_description、control_model_info_label，各一次。前三键来自 p1_fc.txt，对照键来自 p1_readonly_model_info.txt。
- 使用真实 ProLine/ProFileName/ProCharLine 类型，无占位符消息只传三个固定参数，不加变参哨兵。输出是栈上数组，不调用释放函数。
- 增加 MESSAGE_BUFFER_PROBE_BEGIN/RETURN。返回事件带 UI_R6_MESSAGE_PROBE、role、key、原始 pro_error、有界文本和有效性/截断标志。原身份日志仍为 UI_R4_R1_DIAG，这是刻意保留的原有事件。

完整源码和 patches/message-buffer-probe.diff 等价；在隔离副本核对基线后 git apply --unidiff-zero --check，再用 git apply --unidiff-zero 应用。只替换源码，不替换资源。

## 2. 为什么改及契约限制

交接包外部哈希及内部4项清单通过，真实SDK原型、容量和无占位符样例已提供，因此可以实现此探针。宏必须先于头文件，避免 C++ 看到空参数原型。该宏可能启用同一编译单元其他 SDK 变参声明；本机必须真实编译整个源文件并检查诊断，不通过强制函数指针转换绕过。

官方同步样例在初始化中使用该接口。这里放在原命令指定之后，避免在指定之前主动预读；仍不能保证不影响后续消息缓存/UI。若探针加入后突然可见，也不能直接认定稳定修复。

输出最多80个宽字符，容量81含终止符。只在返回0或 PRO_TK_MSG_TOO_LONG(-32)时有界检查文本；其他状态不读输出，text/长度/终止状态分别为null。扫描最多81单元，未终止或UTF-16代理项无效则不输出文本，保留错误和元数据。文本用ASCII JSON的Unicode转义保存，上限483字节，完整日志格式有界。没有截断后继续假装字符串完整的路径。

新的完整消息格式契约说明：四行分别是键、格式串、译文、保留行。过去把后两行统称“分隔符/填充行”并不准确。R5 的 #/# 是未成功的候选，不能当作强制格式规则；本轮冻结该候选，若实际返回“#”、空文本或不同译文，原样记录，不自动改回空行。

面计数描述原格式串81字符，ModelInfo描述82字符，但本轮对照仅解析其短标签。ToBuffer 自身80字符限制可能产生-32；它与 Designate 接收消息键的 char[81] 契约不同，不能凭一次截断归因 UI 缺失。当前语言实际译文也可能改变长度。

## 3. 本机验收步骤与通过信号

本机助手按固定工具链离线重编、链接，核验新源码/DLL哈希、原导出/依赖及两个plus引用。云端没有真实SDK，不能代替此步骤。不要重新采集版本，不改 SDK 头文件，不删宏绕过原型错误。

保留 R5 p1_fc.txt 两份哈希 67ad64e62c6e9e57a04c487ae5e273aa09eac1bc493ca982d5f1775ea7bab4c5，两个旧命令资源亦保持原字节；沿用隔离候选和DAT根到text/<language>关系，不改变语言/模式/过滤条件。

由用户按既有流程手动一次受控加载和列表观察，不部署正式版本。本次只需收集最新pid/load_token的完整初始化段及必要列表截图；不要求绑定或点击面计数、打开/切换模型。

预期原六项注册返回及初始化返回仍为0；原三个身份事件后出现四组探针BEGIN/RETURN，顺序和键与本包相符。所有SDK解析结果都应原样记录，不预设必须为0。返回0且文本有效是该次解析成功；不证明UI可见或精确文件来源。填写 acceptance.template.json。

## 4. 失败和结果分支

- 编译/链接失败：回传真实诊断，停止现场操作。不伪造SDK声明，不改回调签名、不用强制转换消除原型检查。
- BEGIN存在而RETURN缺失：定位最后的role/key，保留日志，不自动重试。此时不能宣称该键已解析成功。
- -4文件未找到、-24无法读取、-28消息未找到、-29无当前语言译文、-30格式错误：分别按真实代码记录，下一轮只修被证据支持的一处。
- -5 E_FOUND：文档指出消息不在内存且文件曾读过，可能涉及同名文件；只记录，不自动刷新/清缓存。
- -32：标记 sdk_reported_truncation=true；text即便存在也只是截断文本，不作为原文完整性或UI根因证据。若截断在代理项中间，text可能为null且text_json_valid=false。
- 原始返回0但未终止/编码无效：记录缓冲契约异常，不继续越界扫描或猜编码。
- 对照成功而面计数键失败：支持资源/键差异调查，业务回调不动。
- 所有键成功但列表仍缺失：消息解析观测通过，GUI仍失败；不能继续断言文件没找到。后续改查有文档依据的命令指定/UI上下文。
- 新项突然可见：可能存在观测影响，不能将加探针视为稳定修复；本轮不额外点击来扩大试验。

接口不暴露绝对路径、语言目录或缓存来源。成功文本只证明本次调用在当前上下文解析出文本，不能证明先前Designate使用同一路径。resolved_path_exposed固定false，不虚构路径回读。
