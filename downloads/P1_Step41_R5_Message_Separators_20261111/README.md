# Step41 R5：仅调整面计数消息文件的记录填充行

日期：2026-11-11（北京时间）。这是基于新增本机官方样例证据的资源格式候选，不是已确认的 UI 修复。本包没有新 DLL、C++ 源码或活动 DAT；无需编译链接。

## 1. 改了什么文件

仅两个语言副本中同一逻辑资源的六行：

- text/chinese_cn/p1_fc.txt
- text/usascii/p1_fc.txt

每组消息的 key/value 后两行，从空行改成字面字符 #，保持每行 LF 换行。例如第一组变为：

```text
P1_BODY_FACE_COUNT_LABEL
p1_readonly_body_face_count
#
#
```

HELP 和 DESC 组做同样修改。两份新文件字节完全相同，都是258字节；原版都是252字节。新 SHA256：67ad64e62c6e9e57a04c487ae5e273aa09eac1bc493ca982d5f1775ea7bab4c5。

消息键、所有值（包括描述现有措辞）、编码、LF 换行、文件名均不改。ModelInfo/Ping 资源不改，不对其他旧候选目录批量应用。同步修改两个语言副本是同一格式变量，避免把语言选择差异混入试验。

可在隔离候选中核验基线后替换这两个文件，也可使用 patches/message-separators.diff：git apply --unidiff-zero --check，通过后 git apply --unidiff-zero。基线资源 SHA256 必须为 c991ea6263a506b16907aa1a13d1ff6147ee730ff9e06d2527ce82b1d0dbefff，不同则停止套用。

## 2. 为什么改

新交接包外部 SHA256 与内部15项文件清单均通过。上传源码与已交付 R4-R1 逐字节相同：7645a55221b1f806e5951290b84ee2eb0e2684a6baa1d9a24753e7b9230dba11。此前身份日志已显示三个 ID 不同、六项调用返回0，但 UI 仍缺面计数。

新增同版契约说明 Designate 返回0表示命令已被指定为可放置，文件或消息未找到有独立错误码；目前“返回成功但列表缺失”仍待解释，不能忽略成功码的文档语义，也不能用它替代 GUI 证据。没有发现额外必须调用图标/刷新的前置要求。

ProCmdItemLabel/LineHelp/Description 的 char[81] 是函数参数中消息键的类型定义；当前传入的键均在长度范围内。数组参数会退化为指针，不能仅凭 typedef 要求每个实际字符数组都必须声明为81字节，更不能将键数组长度直接当成解析后显示文字/说明的上限。ProFileName[40] 同理；当前短文件名长度也在范围内。故本轮不改数组分配形态、标签长度或优先级。

新证据 sdk-contract-snippet.md 第7节报告同版官方 CreoTkExamples_msg.txt 使用 key/value/#/#。现有文件是 key/value/空行/空行，这是现在可与官方样例直接对照的一处差异。本轮只让缺失命令的资源采用该样式，测试其在当前工程中的兼容性。

这不是“空行必定非法”的证明。两个已可见命令也用空行；官方样例只能证明其采用了这种形式，不能单凭样例推出强制规则、缓存机制或根因。云端依据本机助手给出的摘录，未独立打开本机SDK原件。

DAT 的 text_dir 指向候选根目录，下面已有 text/chinese_cn 与 text/usascii，布局与提供的帮助规则相符。本轮不改 text_dir，也不新建根层同名消息文件或猜语言回退顺序。

## 3. 预期通过时看到什么

本机助手先离线准备隔离候选，只替换上述资源。复用经过身份核对的 R4-R1 DLL，记录其哈希且确认未变化；本轮不要编译新 DLL、不要改源码中的日志 revision。DAT 若按既有候选克隆规则调整绝对定位，只保持原有根目录到 text/<language> 的关系，不改注册字段语义。

核验两个新资源哈希、ModelInfo/Ping 原哈希及 DLL 原哈希。不覆盖正在使用的候选资源，不同时让多个候选生效。保留旧副本即可按原字节回滚；本包不执行任何部署操作。

按已有流程由用户手动进行一次受控加载/列表观察即可，不部署正式版本、不自动启动/停止 Creo。只看最新 pid/load_token 的初始化。DLL 未改，日志仍应显示 UI_R4_R1_DIAG，而非 R5；这不是候选未生效的判据。R5 身份靠资源哈希、候选定位与原 DLL 哈希共同记录，不能把日志中的文件基名当成 SDK 文件解析路径回读。

预期六项调用仍返回0、初始化仍为0；在相同模型、当前模式、显示范围和过滤条件下，记录面计数相关项是否出现及实际名称（原显示文字 p1_readonly_body_face_count 或 SDK 键 p1_readonly_fc）。UI 列表按名称排序，不按行号推断注册先后。两个旧命令无须重复点击。

若新项可见且绑定身份清楚，可沿用既定只读验收流程绑定并手动点击一次，保留 BODY_FACE_COUNT_ENTER/RETURN。没有当前模型时的 no_active_model 只能证明触发路径，不是面数量验收。看不到新项或身份不清则不点击，也不为本轮另开/切换模型。

## 4. 失败或不同结果如何分支

- 资源或 DLL 哈希不符合预期：先解决候选身份差异，不把结果归因于消息格式。
- 任一 Add/Designate 非0：记录准确码和最新初始化段，按同版文档区分文件/消息未找到或输入问题；不改回调来绕过。
- 返回全0且新项可见：支持这处资源格式修改在此次条件下有效，但不能直接宣称所有空行非法或稳定根因已证实。仍分开记录 UI 可见与回调/面遍历验收。
- 返回全0但仍不可见：本候选没有解决本次观察。若实际文件解析路径仍未证明，不能进一步断言格式因素被彻底排除。停止继续改名或混改消息键，下一步只补一个有真实 SDK 声明支撑的消息解析观测点；不在本包猜函数名或增加 API。
- 可见但无触发日志：分开调查按钮绑定与业务回调，不把 UI 成功当成计数成功。

填写 acceptance.template.json，连同最新初始化/可选触发段及必要截图回传即可；不重复采集工具链、类型定义、官方帮助或相同资源旧字节。

旧 tools/audit_resources.py 的 structural_parity_pass 特意只比较旧空行样本，所以它会把新 #/# 形式判为不符合旧样本结构；它不是 SDK 解析器。不要用这个字段否决新候选，使用本包逐字节差异、记录值保持及哈希验证。

## 5. 不做什么

不改 DLL、C++、注册顺序、SDK 动作键、消息键/值、显示文字、access、标志、优先级、日志、模型信息或面计数逻辑。不新增图标、菜单、刷新、别名或任何 SDK API。不改 DAT 字段语义、config.pro、CRT、plus 链接、语言设置，不删除缓存/重置 UI，不批量修改旧候选文件。

不打开、选择、修改、保存或转换模型。云端只完成哈希、消息记录字节及补丁应用检查，没有调用 SDK 消息解析器、构建 DLL 或验证真实 GUI。本包不分发上传的原始截图、SDK文档、用户路径或完整源码。
